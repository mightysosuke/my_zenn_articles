実は、新しい技術を学ぶ際に「ゼロから覚える」必要はありません。 すでに皆さんが持っている「RailsやJavaの知識」を基準にして、「何が同じで、何が違うのか」を整理することで、スムーズにキャッチアップできるようになります。

今回は、Web開発に欠かせない「データベース・マイグレーション」を題材に、複数のツール（Railsのmigrate, Ridgepole, Prisma, golang-migrate）を比較しながら、エンジニアが新しい技術を学ぶ時の「頭の中」を公開します。
なお、これら全てを過去や現在の案件で使用したり、ゼロから整備したりしてきたので、本当の事例となります。

## Railsのマイグレーションのおさらい
まず、比較の基準となる「Railsのマイグレーション」を整理しましょう。 Railsのマイグレーションでは、「データベースに対してどのような変更操作を行うか」を手順書のように記述するスタイルを取っています # TODO: 手順書？

【実行フロー】
- `rails g model User name:string`を実行し、マイグレーションファイルを生成する。
- 生成されたファイルを編集して、カラムなどを追加する。
- `rails db:migrate`を実行して、変更をデータベースに適用する。

【コード例】

```ruby
# db/migrate/20231201000000_create_users.rb
class CreateUsers < ActiveRecord::Migration[7.0]
  def change
    # 「テーブルを作成せよ」という命令を書く
    create_table :users do |t|
      t.string :name
      t.timestamps
    end
  end
end
```

【ポイント】
- 差分積み上げ型: 変更履歴（Create Table, Add Columnなど）がファイルとして積み重なっていく。
- 抽象化: Rubyのコードで書くため、SQLを直接意識しなくて良い。

## 他のツールは？
では、現場でよく使われる他のマイグレーションツールを見てみましょう。Railsと比較することで特徴が浮き彫りになります。

### ケース1：Prisma (Node.js/TypeScript)
Prismaは、現在TypeScript環境でよく使われるORMです。Railsとはアプローチが逆です。

【実行フロー】
- `schema.prisma`という定義ファイルを直接編集し、モデルのあるべき姿を書く。
- `npx prisma migrate dev`を実行する。
- Prismaが「現在のDB」と「schemaファイル」の差分を検知し、SQLファイルを自動生成・実行する。

【コード例】

```prisma
model User {
  id        Int      @id @default(autoincrement())
  name      String
  createdAt DateTime @default(now())
}
```

【Railsと異なる点】
- アプローチの逆転: Railsは「マイグレーションファイルを書く→スキーマが決まる」ですが、Prismaは「スキーマを書く→マイグレーションファイルが作られる」という順序です。
- 宣言的: 「どうやって変更するか」ではなく「最終的にどうなっていて欲しいか」を書くため、直感的です。

### ケース2：Ridgepole (Rails)
Ridgepoleはクックパッド社発のツールで、Railsプロジェクトでも採用されることが多いですが、概念はRails標準と大きく異なります。 アプローチは**「完全な宣言的状態管理」**です。

【実行フロー】
- `Schemafile`というたった一つのファイルを編集し、テーブル定義を書く。
- `bundle exec ridgepole --apply`を実行する。
- ツールが自動的に「現在のDB」との差分を計算し、必要なSQLなどを発行して同期させる。

【コード例】

```ruby
create_table "users", force: :cascade do |t|
  t.string "name"
  t.datetime "created_at", null: false
  t.datetime "updated_at", null: false
end
```

【Railsと異なる点】
- ファイル管理: Railsのように大量のマイグレーションファイルを管理する必要がありません。
- 冪等性(べきとうせい): 何度コマンドを実行しても、定義ファイルとDBの状態が一致するようにツールがよしなに計らってくれます。

### ケース3：golang-migrate (Go)
Go言語のエコシステムでは、フレームワークの魔法に頼らないシンプルなツールが好まれます。 アプローチは**「SQL中心（Raw SQL）」**です。

【実行フロー】
- マイグレーション作成コマンドを実行し、up.sql（適用用）と down.sql（ロールバック用）の空ファイルを生成する。
- そのファイルに生のSQLを自分で記述する。
- コマンドを実行して適用する。

【コード例】

```sql
CREATE TABLE users (
  id SERIAL PRIMARY KEY,
  name VARCHAR(255) NOT NULL,
  created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

【Railsと異なる点】
- 抽象化なし: Railsの t.string のような便利なエイリアスはありません。直接 VARCHAR や TEXT などを指定します。
- 明示性: データベース固有の機能を使いたい場合、Railsよりも直接的に記述できます。

## 共通点を見つける
バラバラに見えるこれらのツールですが、エンジニアの視点で「抽象化」すると、**「やっていることは結局同じ」**であることに気づきます。

どのツールも、以下の課題を解決するために存在しています。

1. バージョン管理: DBの状態を「いつ、誰が、どう変えたか」管理したい。
  - Rails/Go: ファイル名のタイムスタンプや連番で管理。
  - Prisma/Ridgepole: 定義ファイルそのもので管理。

2. 整合性の確保: 本番環境、開発環境、テスト環境でDBの構造を一致させたい。
  - どのツールも「定義（コード）」を正として、DBをそれに合わせる動きをします。

### キャッチアップのコツ
私はこれらをキャッチアップする時、以下のように脳内変換しています。
  - 基準と紐付ける: 「これはRailsで言うところの rails g model にあたる操作だな」
  - 差分を言語化する: 「Railsは手順を書くけど、Prismaは結果を書けばいいんだ。ここが違うな」
  - 背景を想像する: 「Goは『隠蔽しない』文化だから、あえて生SQLを書かせるんだろうな」

最後に
ツールや言語が変わっても、「データベースの構造を安全に変更・管理したい」という目的は変わりません。

もし今後、現場で見たことのないマイグレーションツールやライブラリに出会っても、焦る必要はありません。**「Railsのマイグレーションと比べてどう違う？」**と問いかけてみてください。

その「差分」を理解した瞬間、その技術はもう「未知のもの」ではなく、あなたの手札の一つになっているはずです。
